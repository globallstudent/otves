# 0006. Talk to the engine in batches of FlatBuffers commands

Status: accepted    Date: 2026-11-08

## Context

The Kotlin app edits a model that the C++ engine owns on its own thread (ADR 0002). A drag sends a command every frame at 120 fps, so each JNI call must be cheap. App and engine versions ship together, but the contract still has to evolve without breaking old files or tests.

## Decision

- `schema/engine.fbs` is the whole contract. Kotlin sends a `Request` of commands: the core commands plus gesture and undo/redo. The engine answers with a `Response` holding:
  - one result per command: an error code and the id of any element it created;
  - the full value of every element that changed, or its deletion;
  - whether undo and redo are available.
- One JNI call carries one request. The request is a direct `ByteBuffer`. The response is a direct `ByteBuffer` that the session owns until its next call.
- Every request passes the FlatBuffers `Verifier`. A buffer that fails it gets `CorruptData` and changes nothing.
- The engine creates element ids (UUIDv7) and reports them, so a command cannot refer to an element created earlier in the same request.
- A session is single-threaded: Kotlin calls it from one engine thread. Bridge functions are `noexcept` and turn any exception into an `Internal` error.
- Schema evolution:
  - Fields are added only at the end of a table, with a default.
  - Enum values never change once released.
  - Nothing is renumbered or removed; it is deprecated instead.
  - C++ maps every enum explicitly, never by cast.
- Versions: C++ uses FlatBuffers 25.12.19. Kotlin code is generated by flatc 25.2.10 to match `flatbuffers-java` 25.2.10, the newest on Maven Central. The wire format is the same.

## Consequences

- Undo, redo, gestures and edits share one path. The app mirrors the model from the changes without reading engine memory.
- Creating an element and then using it takes two requests. Kotlin-made ids can remove that later without breaking the schema.
- Two flatc versions must be kept in step until `flatbuffers-java` catches up.
